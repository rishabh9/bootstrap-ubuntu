# AI Workstation — resume handover

## Intent and priorities

Simplify an existing Ubuntu AI workstation without reinstalling it. Priorities:
simplicity, maintainability, security, performance and flexibility, in that order.
Workloads: local LLM inference, software development/coding agents and self-hosted
services. Training/fine-tuning is only a possible future workload.

Hardware: Ryzen AI Max+ PRO 395, Radeon 8060S/gfx1151, 128 GB unified memory,
Crucial P310 2 TB OS SSD and Crucial P510 2 TB secondary SSD. Keep physical disks
independent; no RAID or spanning filesystem. Keep Limine and existing encrypted
Btrfs OS layout. The repository is historical and not a reliable live inventory.

## Agreed direction and authorization limits

Retire Incus and use P510 as an encrypted Btrfs /data filesystem with models,
services, projects, datasets and scratch directories sharing capacity. Reuse the
existing partition; fresh LUKS formatting creates a new volume key so the exposed
old key/header cannot unlock future data. All Incus data is explicitly disposable.

Store the new secondary unlock key only inside encrypted root; unlock after root
is available. Retain a tested secondary recovery passphrase. Keep OS encryption,
partitions, installation and Limine binary intact. Boot images/configuration do
need controlled changes. Rootless Podman is the proposed primary service runtime;
use VMs for higher-risk untrusted code rather than assuming kernel-sharing
containers provide VM isolation. Do not add VM/GPU infrastructure prematurely.

User confirmed backup, recovery USB and OS passphrase are ready. The user has NOT
approved execution of the supplied migration apply stages. The current request
authorizes committing and creating this backup PR, with redacted public reports
and a complete local archive. Do not infer migration execution approval from it.

## Prepared artifacts and execution checkpoint

`tools/migrate-workstation.sh` is a machine-specific draft. Default mode only
prints the plan. It has terminal/confirmation checks and two explicit stages:

1. `boot-cleanup`: validate identities, test root passphrase, create backups within
   encrypted root, remove secondary-key embedding, temporarily suspend the Limine
   update hook, rebuild and inspect both retained images, publish matched pairs.
2. Mandatory manual reboot and verification of Ubuntu, networking and Lemonade.
3. `data-migration`: recheck local/default Incus resources and actual P510 backing
   identity, delete disposable dependencies, close old mapping, recreate ONLY P510
   encryption/Btrfs, enroll and test new key/passphrase, mount /data, remove packages.
4. Reboot again and verify unlocking, mounts, services and recovery.

Review tools/MIGRATION.md for exact limits and recovery. In particular:

- A root snapshot alone does not include the ESP.
- Kernel/initramfs pair publication is not an atomic two-file transaction.
- No automatic retries after a partly completed destructive stage.
- Never restore the OLD P510 header after recreating it.
- Old key/header backups remain sensitive for OLD data copies even after reformat.
- Existing Limine hook rotation reliability still needs a later maintenance fix.
- Incus APT source/key and group cleanup is deferred until shared dependencies
  are checked; new header backup must reach independently encrypted external storage.

The scripts passed syntax checks and four CLI safety tests; an independent static
review found no remaining blockers after local Incus remote/project and backing
pool checks were added. This is NOT evidence of successful live migration. All
destructive operations and reboot checkpoints remain pending.
